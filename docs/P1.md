
# P1 — Threat Library + Red Team Controller

### P1 objective

Turn the P0 simulator into a real **Red Team Lab** that can select, replay, mutate, and evaluate known payment-fraud threats.

P1 is **not yet the novel autonomous attack-discovery system**. That comes later. P1 establishes the reliable attack infrastructure that the future reasoning agents will use.

The P1 loop is:

```text
THREAT LIBRARY
      ↓
RED TEAM CONTROLLER
      ↓
SELECT ATTACK
      ↓
CONFIGURE ATTACK
      ↓
ATTACK SIMULATOR
      ↓
BLUE TEAM
      ↓
DETECTION RESULTS
      ↓
ATTACK EVALUATION
      ↓
RED TEAM REPORT
```

---

# P1.1 — Threat Library

Create a structured threat registry.

Do not store threats as plain Markdown descriptions. Every threat must be executable through a common schema.

### Initial library

Start with approximately **10–15 threats**, including the five P0 attacks plus additional families covering different attack surfaces.

Recommended initial set:

```text
ATO-001     Account Takeover
VEL-001     Velocity Attack
AMT-001     Amount Anomaly
BEN-001     Beneficiary Anomaly
SLOW-001    Low-and-Slow Fraud

DEV-001     Shared Device Fraud
IP-001      Shared IP Coordination
MUL-001     Mule Account Network
MER-001     Merchant Coordination
FRAG-001    Payment Fragmentation

GEO-001     Geographic Anomaly
SEQ-001     Suspicious Transaction Sequence

AGT-001     Agent Scope Abuse
INT-001     Intent Mismatch
```

The exact final list can be adjusted based on the P0 data capabilities, but every threat must be **simulatable using the synthetic environment**.

### Threat schema

```text
attack_id
name
category
evidence_level
objective
target
attack_surface

required_features
mutation_strategy
```

# P1.3 — Red Team Controller

Build a deterministic controller first.

The controller should answer:

> Which known attack should I run, against which target population, at what intensity and scale?

Inputs:

```json
{
  "attack_id": "ATO-001",
  "intensity": "HIGH",
  "transaction_count": 10000,
  "target_population": "normal_customers",
  "seed": 424242
}
```

Output:

```text
Simulation ID
Attack ID
Parameters
Generated entities
Generated transactions
Ground-truth labels
```

# P1.4 — Attack difficulty

Every attack needs at least:

```text
LOW
MEDIUM
HIGH
```

Later:

```text
ADAPTIVE
```

For example:

### Account takeover

**LOW**

```text
New device
Large amount
New location
```

**MEDIUM**

```text
New device
Moderate amount deviation
Moderate location deviation
```

**HIGH**

```text
Known device
Normal amount
Normal merchant
Subtle behavioral deviation
```

This gives the Blue Team a meaningful stress-testing gradient.

# P1.5 — Attack mutation engine

Instead of hardcoding one fraud pattern, create parameterized mutations.

Example:

```text
base transaction
      ↓
mutation configuration
      ↓
fraud variant
```

Example:

```json
{
  "amount_deviation": 0.15,
  "velocity_multiplier": 2.1,
  "geo_deviation": 0.05,
  "device_change_probability": 0.00,
  "beneficiary_change_probability": 0.60
}
```

This is important because P1 should be able to generate **many variants from one threat definition**.

# P1.9 — Red-Team benchmark system

This is the part you asked to lock in.

P1 cannot be considered complete until it passes a benchmark suite.

## P1 Benchmark A — Threat Library Coverage

Minimum:

**10 executable threat definitions**

with:

* valid schemas
* simulation templates
* expected signals
* test cases

Target:

**≥ 95% valid threat definitions**

No broken attack templates.

---

## P1 Benchmark B — Reproducibility

Run the same attack twice:

```text
same seed
same parameters
same source data
```

Expected:

```text
Identical transaction generation
Identical labels
Identical graph relationships
Identical metrics
```

Target:

**100% reproducibility**

---

## P1 Benchmark C — Attack Scaling

Each core attack must support at least:

```text
1,000
10,000
100,000
```

synthetic events, hardware permitting.

The attack generator must not change the underlying distribution merely because scale changes.

Target:

**≥ 95% successful generation jobs**

---

## P1 Benchmark D — Attack Diversity

For each core attack:

**≥ 5 distinct variants**

without simply duplicating rows.

Target:

**≥ 50 valid attack variants across the initial library.**

---

## P1 Benchmark E — Difficulty Gradient

For at least 5 attack families:

```text
LOW
MEDIUM
HIGH
```

must produce measurably different detection difficulty.

Expected:

```text
Detection(LOW)
>
Detection(MEDIUM)
>
Detection(HIGH)
```

Not necessarily in every random run, but the aggregate benchmark should demonstrate a statistically meaningful difficulty gradient.

---

## P1 Benchmark F — Attack Fidelity

Synthetic attacks must remain statistically close to the underlying legitimate/fraud distributions.

Define thresholds using the P0 baseline rather than inventing arbitrary universal numbers.

For each attack verify:

* amount distribution
* temporal distribution
* merchant distribution
* velocity
* major behavioral correlations

Target:

**No major distribution drift introduced solely by the simulator.**

The exact accepted distance threshold should be established from the P0 baseline fidelity measurements.

---

## P1 Benchmark G — Blue-Team Stress

This is important:

We **want some attacks to bypass the current detector**.

Across the attack library, the Red Team should produce:

```text
Easy → high detection
Medium → moderate/high detection
Hard → lower detection
```

The system should identify at least some genuine weaknesses.

A good P1 result might look conceptually like:

```text
Easy attacks:    95–99% detected
Medium attacks:  85–95%
Hard attacks:    60–85%
```

These are **target bands, not fabricated requirements**. We should use the actual P0 detector performance to calibrate them.

---

## P1 Benchmark H — No Label Leakage

Critical.

The Blue Team must not receive:

```text
attack_id
attack_type
simulation_id
ground_truth attack name
```

as predictive features.

Target:

**0 known leakage paths**

This must be tested automatically.

Once P1 passes, we move into the first major intelligence expansion:

## P2 — Network + Geo Intelligence

We'll add:

```text

IP
Merchant
Beneficiary
Agent

```

as a connected graph.

Then:

```text
Graph features
+
Geo features
+

        ↓
Blue Team V2
```

The P2 benchmark will specifically ask:

> **Does network + geographic intelligence detect attacks that P1's transaction-level Blue Team misses, without causing unacceptable false positives?**

That gives us a clean scientific progression:

```text
P0

       ↓

       ↓

       ↓
P3

       ↓

       ↓

       ↓

```

That is the development path I recommend locking in.
