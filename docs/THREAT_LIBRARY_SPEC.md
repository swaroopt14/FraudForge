## 1. Purpose

The Threat Library is the evidence-backed knowledge base for the Adversarial Payment Defense Lab.

It stores:

- Historical fraud patterns.

- Research-derived threat patterns.

- Payment attack behaviors.

- Network and graph motifs.

- Agent and intent abuse patterns.

- Simulation templates.

- Detection signals.

- Mitigation playbooks.

- Red-team attack hypotheses.

- Compiled attack specifications.

- Blue-team evaluation results.

- Loop intelligence reports.

The Threat Library is not only a document repository. It is the source of structured objects that can be:

1. Retrieved.

2. Compared.

3. Replayed.

4. Mutated.

5. Composed.

6. Validated.

7. Compiled.

8. Simulated.

9. Evaluated against the Blue Team.

10. Improved through feedback.

## 3. Core Design Principles

### 3.1 Evidence before generation

Every historical or research-derived threat must contain source references.

A generated hypothesis must identify:

- Which threats it was based on.

- Which blue-team failures influenced it.

- Which patterns were combined.

- Which parts are known.

- Which parts are inferred.

- Which parts are newly hypothesized.

The system must not present generated hypotheses as confirmed real-world incidents.

### 3.2 Structured data before natural language

Natural-language descriptions are useful for analysts and reasoning models.

However, the simulator and detector require structured fields such as:

- Attack family.

- Attack steps.

- Payment behavior.

- Network behavior.

- Agent behavior.

- Intent behavior.

- Observable signals.

- Simulation parameters.

- Realism constraints.

### 3.3 Agents reason; deterministic systems execute

The Cyber Reasoning Agent may:

- Interpret evidence.

- Generate hypotheses.

- Propose attack combinations.

- Explain novelty.

- Recommend next attack directions.

The Cyber Reasoning Agent must not directly:

- Execute real payments.

- Call production payment APIs.

- Modify production records.

- Generate credentials.

- Send messages to real victims.

- Write and execute unrestricted attack code.

- Override policy controls.

### 3.4 Models detect; policies enforce

Machine-learning models produce risk scores.

Deterministic policy services enforce:

- Intent limits.

- Agent permissions.

- Destination binding.

- Authentication requirements.

- Spending limits.

- Simulation-only restrictions.

- Allowed payment rails.

- State transitions.

### 3.5 Simulation only

Every attack generated by this system must run against:

- Synthetic identities.

- Public or synthetic datasets.

- Mock merchants.

- Mock tools.

- Mock agents.

- Local payment simulators.

- Local detection services.

No real payment, account, credential, or victim may be used.

## 7. Historical Status

Every threat must have one of the following statuses.

| Status | Meaning |

|---|---|

| `historical` | Based on a documented incident or official report |

| `research_derived` | Derived from research or threat intelligence |

| `mutation` | A controlled variation of a known pattern |

| `composite` | Combination of two or more known patterns |

| `hypothesis` | Proposed but not yet validated |

| `simulated` | Generated and executed in the simulation environment |

| `candidate_novel` | Structurally different from the current history |

| `confirmed_novel` | Reserved for externally validated new activity |

The system must not use `confirmed_novel` for an internal generated attack unless there is external evidence.

## 12. Cyber Reasoning Agent

The Cyber Reasoning Agent is responsible for reasoning over threat knowledge.

### It may:

- Summarize historical fraud.

- Compare multiple attack patterns.

- Propose composite attacks.

- Identify missing detector signals.

- Suggest realistic evasions.

- Generate attack hypotheses.

- Recommend simulation parameters.

- Explain why an attack is different from history.

### It may not:

- Directly generate real credentials.

- Execute payment APIs.

- Contact victims.

- Modify production systems.

- Write unrestricted attack code.

- Bypass validation.

- Mark its own output as confirmed fraud.

- Override a deterministic policy.

### Required output

The agent must return a structured Attack Hypothesis.

## 14. Novelty Evaluation

Novelty must be calculated across multiple dimensions.

### 14.1 Semantic novelty

Compare the hypothesis embedding with historical hypothesis embeddings.

```text

semantic novelty =

1 - maximum semantic similarity to prior attacks

```

### 14.2 Sequence novelty

Compare the attack-step sequence with previous sequences.

```text

create_identity

→ add_beneficiary

→ submit_payment

```

is less novel than:

```text

agent_tool_call

→ destination_change

→ spending_fragmentation

→ multi-agent_coordination

```

### 14.3 Graph novelty

Compare:

- Node-type distribution.

- Edge-type distribution.

- Degree structure.

- Fan-in/fan-out behavior.

- Community structure.

- Beneficiary concentration.

- Agent-tool relationships.

### 14.4 Behavior novelty

Compare:

- Amount distribution.

- Velocity.

- Merchant sequence.

- Device behavior.

- Timing.

- Cumulative intent spending.

- Authentication pattern.

### 14.5 Combined score

```text

novelty_score =

    0.25 × semantic_novelty

  + 0.25 × sequence_novelty

  + 0.25 × graph_novelty

  + 0.25 × behavior_novelty

```

The score should be called:

```text

candidate novelty

```

It must not be described as a confirmed real-world zero-day.

## 15. Threat Validator

The Threat Validator is a hard gate between reasoning and compilation.

### Validation layers

```text

Schema validation

      ↓

Taxonomy validation

      ↓

Evidence validation

      ↓

Simulator capability validation

      ↓

Payment realism validation

      ↓

Network realism validation

      ↓

Agent/intent consistency validation

      ↓

Safety validation

```

### Validator checks

#### Schema

- Required fields exist.

- Values have correct types.

- Attack family is recognized.

- Template names exist.

#### Evidence

- Historical claims have sources.

- Inferences are labelled.

- Generated claims are labelled as hypotheses.

#### Simulator capability

- Requested payment rail is supported.

- Required entity types exist.

- Required event types exist.

- Requested agent behavior is representable.

- Requested network structure is implementable.

#### Payment realism

- Amount is positive.

- Currency is supported.

- Event sequence is valid.

- Beneficiary exists before payment.

- Intent exists before agent action.

- Payment status transitions are valid.

#### Network realism

- Relationships are temporally possible.

- Device and IP reuse follows configured limits.

- Graph is not accidentally fully connected.

- Beneficiary concentration is parameterized.

- Fraud and legitimate shared infrastructure are both possible.

#### Safety

- No live execution.

- No real credentials.

- No real victim targeting.

- No harmful payload generation.

- No production API access.

## 24. Definition of Done

The Threat Library is ready for the next phase when it can:

1. Store an evidence-backed historical fraud type.

2. Retrieve similar threats.

3. Replay a known attack.

4. Generate a controlled mutation.

5. Combine two known patterns.

6. Produce a structured attack hypothesis.

7. Calculate candidate novelty.

8. Reject unsupported or unsafe hypotheses.

9. Compile an approved hypothesis into synthetic events.

10. Run the events through the Blue Team.

11. Store detected and missed outcomes.

12. Produce a Loop Intelligence Report.

13. Generate a next-round red-team direction.

14. Record all versions and seeds.

## 25. Final Principle

The Threat Library is successful only when it transforms knowledge into measurable defensive testing.

```text

Historical fraud

      ↓

Structured attack pattern

      ↓

Replay

      ↓

Mutation

      ↓

Composition

      ↓

Novel attack hypothesis

      ↓

Validation

      ↓

Compilation

      ↓

Synthetic transaction + network + agent events

      ↓

Blue-Team evaluation

      ↓

Failure report

      ↓

Harder Red-Team attack

      ↓

Stronger Blue-Team model

```

The library must generate attacks with both:

- Breadth across fraud families, payment rails, networks, and agent behaviors.

- Depth across identity, behavior, relationships, intent, execution, and settlement.

It must remain evidence-backed, simulation-only, reproducible, explainable, and measurable.
